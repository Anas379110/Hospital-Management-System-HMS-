# FR4.4 encounter logical deletion UI plan
Source: SRS FR4.4 and existing DELETE/encounters/:id controller/DTO/service, patient records and clinical-response tests. Development/testing uses fictional data only. No real-record deletion authorized.
Scope: owner-doctor/admin per-record confirmation, required reason >=5 characters, fresh GET identity/ownership preflight and strict DELETE200 response identity/deletedAt/reason. No backend/schema/role/policy/retention change. No restore/permanent deletion.
Existing semantics: deleted encounter disappears from current records and GET returns404; underlying row/prescriptions retained, completed test history retained, linked appointment remains consumed. Confirmation must say this. No claim legal compliance is established by the UI.
No automatic retries. Definite4xx preserves reason. Unknown write outcome persists an encounter-specific hold across reload; explicit check reads current encounter visibility plus current patient history, never treats GET404 as proof this request committed. Review/discard closes the held UI, not a retry or success assertion. Session/route guards before and after await prevent stale DELETE dispatch and UI effects. Clear only matching current prescription/test-order targets after verified success. No broad tests repeated solely for pixels.
