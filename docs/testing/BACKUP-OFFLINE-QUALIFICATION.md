# Local backup and disconnected-browser qualification

27 November 2026. Original restore/offline executions used runtime source baseline 37424a3 and retain that provenance in their reports. They were published with ecc4400, whose only runtime change was the frontend i18next security patch. The separate attendance candidate below does not relabel those earlier executions as current-head runs. These are bounded engineering checks, not completion of the original intranet/daily-backup target.

## Logical restore drill

`backend/test-real-postgres/backup-restore.mjs` was executed against fresh dedicated loopback PostgreSQL17.12 and 18.7 clusters. Each fixture was generated by the existing actual-HTTP `performance.mjs` runner. No hosted database was accessed.

The runner requires two distinct `hms_test_perf_*` database names, an explicit loopback port and a real `/tmp/hms_test_perf_*` data directory. Both databases must return the same expected actual `SHOW data_directory` before dump/restore. System identifiers must also match and the local postmaster PID must exist. Target tables and public functions must be absent. Restore uses a custom-format archive, `--exit-on-error --single-transaction`, and no clean/drop/overwrite options. Source remains unchanged.

Results in `evidence/backup-restore-pg{17,18}-20261127.json`:

- Every public table's count and ordered JSON row digest matched after restore, including 10040 fictional patients and 40 audits, migration records and workspace metadata.
- RLS/FORCE RLS flags, 15 policies, 178 table grants, constraints, 4 functions, indexes, triggers, enum labels, column types/defaults and schema/function ACLs matched. PostgreSQL18 reports more constraints because of its catalog representation; comparisons are within each server, not across major versions.
- Restricted `hms_runtime` after restore sees 10040 patients in its workspace and zero in an absent workspace. UPDATE of audit logs remains denied.
- After immutable restore comparisons, a second real fictional workspace was created in the target. Restricted-role reads of patients/users/departments in each workspace returned only that workspace, with expected counts and no foreign rows. Role attributes are non-superuser/non-BYPASSRLS and ownership is excluded; UPDATE/DELETE/TRUNCATE audit privileges are denied. This is selected-table isolation, not all-role/all-table certification.
- Source rows and explicitly measured catalog objects still matched the pre-dump snapshot. This is not a universal catalog equivalence proof.

The local fictional archives are retained in private mode 0600 under mode 0700 temporary directories. This is not a protected long-term backup store.

### Reproduction

Use a separately created, dedicated local cluster with already-installed compatible PostgreSQL clients and Node dependencies. Never point these commands at hosted/shared databases. First run `performance.mjs` against a fresh empty source using `HMS_PERFORMANCE_DATABASE_URL` and `HMS_TEST_PG_DATA`; it applies repository migrations and creates fictional fixtures/local test roles. Create a second empty database in that same dedicated cluster. Then from `backend`:

```sh
HMS_BACKUP_SOURCE_URL="$LOCAL_SOURCE_URL" \
HMS_BACKUP_TARGET_URL="$LOCAL_EMPTY_TARGET_URL" \
HMS_TEST_PG_DATA="$LOCAL_DISPOSABLE_DATA_DIR" \
HMS_TEST_PG_DUMP="$MATCHING_PG_DUMP" \
HMS_TEST_PG_RESTORE="$MATCHING_PG_RESTORE" \
HMS_BACKUP_REPORT=backup-restore-report.json \
node test-real-postgres/backup-restore.mjs
```

URLs are supplied privately by the local test harness, never committed. The database names and actual data directory guards are mandatory. `pg_dump`/`pg_restore` must match/support the server version. The drill reuses cluster-global roles already present, so it does not establish disaster recovery onto a new host. Whole-database logical archives include fictional workspace/account state, not external secrets/configuration.

Still unqualified: scheduled daily backup, agreed retention, independent storage/copy, encryption/key custody, global role reconstruction, a clean new-host restore, automated restore alerts, PITR, physical disk/power failure, or an accepted RPO/RTO. Archive existence alone is not restoration evidence.

## Browser external-network denial

`frontend/test-real-browser/offline-runtime.mjs` was run against compiled production frontend assets served by the actual compiled Nest backend and a restored disposable PostgreSQL18 DB. The browser routing handler rejects every non-local HTTP(S) request and WebSocket. Service workers are blocked.

Measured paths: login page load, fictional workspace bootstrap via API 201 plus token injection, patient search-results display, appointment list/options, department directory and native Swagger 44 operations. No login form submit, UI start-button flow or patient detail view is claimed. Appointments/directory headings are explicitly checked. All requested browser scripts/styles/API paths remained local; no external HTTP(S)/WebSocket attempts or page errors were observed. Source inventory agrees for these paths. Desktop directory/Swagger and 390 px mobile patient screenshots were inspected: readable, no horizontal clipping. Evidence: `evidence/offline-runtime-20261127.json`.

Run from `frontend` with `HMS_OFFLINE_DATABASE_URL`, `HMS_TEST_PG_DATA`, optional `HMS_OFFLINE_REPORT` and `HMS_OFFLINE_ARTIFACTS`. It starts the existing compiled app on loopback, not Vite. The local-only harness resets the existing test runtime role password, then connects the app with actual `hms_runtime` credentials. A separate connection using the exact same URL asserts both current_user and session_user are `hms_runtime`; no owner credentials are passed to the app. This is not new-host role recovery. It creates one additional fictional workspace in the restored target; this happens after the immutable restore checks.

This is not an OS network namespace, packet capture, a full physical internet-disconnection test or an exhaustive route/workflow test. Node/PostgreSQL egress was not blocked by this browser harness. Preinstalled dependencies were necessary. A new offline installation has not been demonstrated. No service-worker/cache, offline queued writes or continued operation when LAN/API/DB is unavailable is claimed.

Current first-party translation setup imports two static JSON dictionaries, with no remote loader/resource upload found. This narrows observed exposure but does not erase the dependency finding. Candidate lint, production build, 40 frontend tests including all dictionary strings/interpolation and inherited-built-in merge regression, and the measured production browser paths pass; fresh audit returns zero vulnerabilities. Exact-head CI/review and hosted verification are still required before release. The deployed 37424a3 still has the older dependency until then.

Reports record script SHA256 and dirty-tree state (backup runner), not merely baseline git HEAD. The runtime report also records its script SHA256. ### Separate attendance CI harness

Attendance uses its own dedicated empty CI database, not the restore target.
`HMS_ATTENDANCE_CI=true` requires GitHub Actions, exact loopback host/port5432,
owner hms_test and database hms_test_attendance with no connection options.
It refuses any existing public table before migrations, creates a distinct
nonowner/no-bypass runtime role and verifies audit UPDATE/DELETE/TRUNCATE denial.
Local mode still requires the actual matching disposable /tmp data directory.
Local CI-path emulation on a fresh PG18 cluster passed; that is not a hosted CI
run. The workflow now runs the same HTTP/browser cases in both PG17/18 jobs,
retaining JSON and screenshots. Report script hashes tie each run to its code.
