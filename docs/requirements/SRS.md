# SRS.md — Software Requirements Specification
## نظام إدارة المشافي (HMS) — نطاق MVP

---

## 1. Functional Requirements

### FR-1 Module: Users & Roles (RBAC)
- FR-1.1: النظام يسمح بإنشاء مستخدم بدور محدد (Admin, Receptionist, Doctor, Nurse, Manager).
- FR-1.2: كل مستخدم يسجّل دخول بـ Username/Password (Hashed).
- FR-1.3: الصلاحيات تُفرض على مستوى API (لا الواجهة فقط) لكل Endpoint.
- FR-1.4: كل عملية حساسة (إنشاء/تعديل/حذف سجل مريض أو طبي) تُسجَّل في Audit Log (من قام بها، متى، ماذا تغيّر).
- FR-1.5: المدير (Admin) فقط يستطيع إنشاء/تعطيل حسابات المستخدمين.

### FR-2 Module: Patients
- FR-2.1: تسجيل مريض جديد (اسم، تاريخ ميلاد، جنس، رقم هوية وطنية إن وجد، عنوان، هاتف، جهة اتصال طوارئ).
- FR-2.2: كل مريض يحصل على رقم ملف طبي فريد (MRN) يُنشأ تلقائياً عند التسجيل.
- FR-2.3: البحث عن مريض بالاسم/رقم الملف/رقم الهاتف.
- FR-2.4: تعديل بيانات مريض موجود (مع تسجيل من عدّل ومتى في Audit Log).
- FR-2.5: منع تكرار تسجيل نفس المريض (تحقق بالاسم + تاريخ الميلاد أو رقم الهوية عند توفره) — يُعرض تنبيه لا حجب تلقائي كامل (القرار النهائي بيد الموظف).

### FR-3 Module: Appointments
- FR-3.1: حجز موعد لمريض مسجَّل مع طبيب/قسم محدد وتاريخ ووقت.
- FR-3.2: منع حجز موعدين متعارضين لنفس الطبيب بنفس الوقت.
- FR-3.3: تعديل/إلغاء موعد مع سبب اختياري.
- FR-3.4: عرض جدول مواعيد يومي/أسبوعي لكل طبيب.
- FR-3.5: تصنيف حالة الموعد: (مجدول / حضر / لم يحضر / ملغى).

### FR-4 Module: EMR أساسي (Electronic Medical Record)
- FR-4.1: عند زيارة (Encounter) مرتبطة بموعد أو دخول طارئ، يستطيع الطبيب تسجيل: الشكوى الرئيسية، التشخيص، الملاحظات السريرية.
- FR-4.2: تسجيل وصفة طبية (اسم الدواء، الجرعة، المدة، ملاحظات) مرتبطة بالزيارة.
- FR-4.3: عرض السجل الطبي الكامل (تاريخياً) للمريض مرتّباً زمنياً — قراءة فقط لغير المخوَّلين بالتعديل.
- FR-4.4: لا يمكن حذف سجل طبي نهائياً (Soft Delete فقط + توثيق السبب) — لأسباب قانونية وتدقيقية.

### FR-5 Module: Departments & Beds
- FR-5.1: تعريف الأقسام (باطنية، جراحة، طوارئ...) وعدد الأسرّة في كل قسم.
- FR-5.2: تسكين مريض في سرير محدد (Admission) وتسجيل وقت الدخول.
- FR-5.3: تفريغ سرير عند خروج المريض (Discharge) مع تسجيل وقت الخروج والحالة.
- FR-5.4: عرض حالة الأسرّة في الوقت الفعلي (متاح / مشغول / تحت الصيانة) لكل قسم.

## 2. Non-Functional Requirements

| الفئة | المتطلب |
|---|---|
| **Performance** | استجابة API الأساسية < 300ms على خادم متوسط الأداء تحت حمل عادي (مصمَّم لسعة 10,000+ مريض مسجَّل) |
| **Security** | تشفير كلمات المرور (bcrypt/argon2)، HTTPS داخل الشبكة الداخلية، Audit Trail شامل، RBAC صارم على مستوى API |
| **Availability** | يعمل بالكامل على شبكة داخلية (Intranet) دون اعتماد على إنترنت خارجي؛ خطة نسخ احتياطي يومي محلي |
| **Scalability** | معمارية Modular Monolith تسمح باستخراج وحدات لاحقاً دون إعادة كتابة كاملة |
| **Reliability** | لا فقدان بيانات عند انقطاع كهرباء مفاجئ (Transactions ذرية + نسخ احتياطي متكرر) |
| **Accessibility** | دعم كامل لـ RTL (عربي) وLTR (إنجليزي)، تباين ألوان واضح لبيئة عمل سريرية |
| **Maintainability** | فصل نصوص الواجهة عن الكود (i18n) من اليوم الأول، توثيق API عبر OpenAPI |
| **Compliance** | متوافق مع قانون سوريا رقم 12/2024 لحماية البيانات الشخصية الإلكترونية (تشفير، سجل تدقيق، سياسة احتفاظ بيانات) |
| **Interoperability (مستقبلي)** | نموذج البيانات مصمَّم بحيث يسهل تعيينه لاحقاً لموارد HL7 FHIR ذات الأولوية لتكامل وزارة الصحة (Patient, Encounter, Condition, DiagnosticReport, Immunization) |

## 3. User Stories + Acceptance Criteria (عيّنة تمثيلية لكل وحدة MVP)

### US-1 (Receptionist)
**كـ** موظف استقبال، **أريد** تسجيل مريض جديد بسرعة، **حتى** أبدأ إجراءات زيارته دون تأخير.
**Acceptance Criteria:**
- الحقول الإلزامية: الاسم الكامل، تاريخ الميلاد، الجنس، رقم هاتف.
- عند الحفظ، يُنشأ رقم ملف طبي (MRN) فريد تلقائياً ويظهر للموظف.
- إذا وُجد مريض بنفس الاسم وتاريخ الميلاد، يظهر تنبيه "قد يكون مسجلاً مسبقاً" مع خيار المتابعة أو الرجوع لسجله.

### US-2 (Doctor)
**كـ** طبيب، **أريد** عرض السجل الطبي الكامل للمريض قبل الزيارة، **حتى** أتخذ قراراً سريرياً مبنياً على تاريخه.
**Acceptance Criteria:**
- عرض كل الزيارات السابقة مرتبة من الأحدث للأقدم.
- عرض كل الوصفات السابقة والتشخيصات.
- لا يمكن للطبيب تعديل زيارة طبيب آخر — قراءة فقط لسجلات الآخرين، إلا بصلاحية خاصة موثقة.

### US-3 (Receptionist)
**كـ** موظف استقبال، **أريد** حجز موعد لمريض مع طبيب محدد، **حتى** ينظَّم دوام الأطباء ولا يحدث تعارض.
**Acceptance Criteria:**
- النظام يمنع حجز موعدين لنفس الطبيب بنفس التوقيت.
- يظهر تأكيد فوري بتفاصيل الموعد بعد الحفظ.

### US-4 (Nurse)
**كـ** ممرض/ة، **أريد** تسكين مريض في سرير متاح ضمن قسمه، **حتى** يبدأ العلاج فوراً عند القبول.
**Acceptance Criteria:**
- لا يمكن تسكين مريض في سرير مشغول بالفعل.
- عند التسكين، تتحدث حالة السرير فوراً إلى "مشغول" لكل من يشاهد اللوحة.

### US-5 (Hospital Manager)
**كـ** مدير مشفى، **أريد** رؤية إحصائية سريعة لعدد الأسرّة الشاغرة لكل قسم، **حتى** أتخذ قرارات تشغيلية فورية.
**Acceptance Criteria:**
- لوحة تعرض لكل قسم: العدد الكلي، المشغول، المتاح، تحت الصيانة — بتحديث فوري (Real-time أو Near-real-time).

## 4. Use Cases (تفصيلية — عيّنة)

### UC-1: تسكين مريض في سرير (Admission)
- **Actor:** ممرض/ة أو طبيب مخوَّل
- **Trigger:** قرار قبول المريض في المشفى بعد الفحص
- **Preconditions:** المريض مسجَّل في النظام، يوجد سرير متاح في القسم المطلوب
- **Main Flow:**
  1. المستخدم يبحث عن المريض بالـ MRN أو الاسم
  2. يختار القسم المطلوب
  3. النظام يعرض الأسرّة المتاحة فقط
  4. المستخدم يختار سريراً ويؤكد
  5. النظام يسجل وقت الدخول ويغيّر حالة السرير إلى "مشغول"
- **Alternative Flow:** لا يوجد سرير متاح → النظام يعرض قائمة انتظار (Waitlist) بدل رسالة خطأ فقط
- **Error Flow:** فقدان الاتصال أثناء الحفظ → النظام يعرض رسالة واضحة ولا يسجل تسكيناً جزئياً (Transaction ذرية)
- **Postconditions:** المريض مسجَّل كمقبول (Admitted)، السرير "مشغول"، سجل Audit محدَّث

### UC-2: صرف وصفة طبية (لاحقاً عند تفعيل وحدة الصيدلية — مرجعية مبكرة)
- **Actor:** صيدلي
- **Trigger:** وصفة طبية مسجَّلة من طبيب
- **Preconditions:** الدواء متوفر في المخزون
- **Main Flow:** عرض الوصفة → التحقق من التوفر → الصرف → خصم الكمية من المخزون
- **Alternative Flow:** الدواء غير متوفر → اقتراح بديل متوفر (إن أمكن) أو تسجيل "نقص مخزون"
- **Postconditions:** تحديث المخزون، تسجيل عملية الصرف
