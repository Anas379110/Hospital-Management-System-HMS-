## Retention

Access expires after24hours idle. Hourly cleanup deletes live workspace metadata and cascades domain/audit records, normally by the next hour. Provider outages, quota exhaustion and suspended service can delay physical deletion. Supabase may pause after7days of low user activity. A paused project may be restored for up to1year. That is a project restore window, not a claim about retention of each deleted record. No Neon6hour recovery claim applies. Cleanup cannot run while paused; quarantine resumed/restored service until cleanup and acceptance finish. No exported visitor backups. Do not promise irreversible erasure at the sweep.

## Restore and rollback

No visitor-data export/import. Provider recovery can resurrect expired workspaces, so quarantine any restored branch from public web access. Run the expiry cleanup with the restricted cleanup identity before binding public traffic. Check that expired test workspace remains inaccessible/deleted and a current fictional control workspace survives. Do not connect production web to a restore point until that check passes. Provider history expires; Free recovery is not a promised business backup.

Rollback application release by restoring the prior reviewed artifact/environment on the new isolated service only. Do not point the isolated application at the old showcase database or deploy frozen PR3 as an isolated demo. If startup fails, leave new service unavailable rather than fall back to an owner credential or shared data.

## Proxy acceptance gate

HMS_TRUSTED_PROXY_ADDRESSES is empty by default, so client-supplied forwarded headers do not pick the rate-limit key. Explicit IP/CIDR allowlists only; true, named ranges, hop counts and universal CIDR are rejected. Do not fill it from guesses about Render's network. Render documents load-balancer TLS termination and forwarding but not an invariant complete proxy-address chain in the checked guides. Verify actual socket peer and forwarded chain on the new fictional service without logging persistent visitor/IP data, then test forged forwarded headers cannot rotate the key and two distinct real clients do not share one key. Set only supported observed proxy addresses if stable; otherwise keep public activation blocked until a supported edge/client identity mechanism is established. Default can over-throttle behind shared proxy, so it is safe against spoofed headers but not launch acceptance. Sources: https://expressjs.com/en/guide/behind-proxies.html and https://render.com/docs/web-services . Assert HMS_PUBLIC_DEMO=true from actual startup behavior, not deployment docs alone.

## Executable resume gate

With public traffic disabled, run backend/scripts/resume-demo-gate.cjs with HMS_TRAFFIC_DISABLED=true, HMS_OWNER_DATABASE_URL, HMS_RUNTIME_DATABASE_URL, HMS_CLEANUP_DATABASE_URL and HMS_RESUME_CONTROL_WORKSPACE identifying an existing unexpired fictional control. Every URL must use verify-full and an existing CA file. The script sends no password in its plaintext StartupMessage probes, requires ESSLREQUIRED for all three logins, runs the owner structural/operational audit and restricted cleanup runner, requires no expired rows and a surviving control, then calls runtime onModuleInit for TLS and grant checks. Missing inputs fail closed. Success does not bind traffic, change a provider state, or prove a real pause happened. Operator must keep the external service quarantined until this succeeds. Actual roles/grants/jobs/SSL-setting persistence across pause remains untested provider behavior. A quiet Free project can become unavailable until an authorized operator resumes it; no instant-resume or deletion-during-pause promise.

A pause longer than90minutes requires waiting for the next successful scheduled cleanup before rerunning the gate. Never bypass freshness. The resume gate explicitly rechecks cleanup-status.sql as owner as well as the operational audit; output fields derive from those returned checks and successful startup rather than stand-alone claims.
